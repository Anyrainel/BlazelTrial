# Decisions

Short decision log. Newest at the bottom. Status: **Accepted** unless marked otherwise.

| # | Area | Decision | Why | Rejected |
|---|---|---|---|---|
| D1 | Hosting | **Local only.** No cloud deploy. | Assignment requires state in SQLite/files inside the repo dir; scale-to-zero clouds have ephemeral disks. | Fly.io (volume + auto-stop), Lambda/Cloud Run + serverless DB. |
| D2 | Runtime state | All runtime data in **`.state/`** (gitignored): `state.db`, `docs/` corpus, `logs/`, `models/`. Paths configurable. | User data and user docs are not source code. | Committing `docs/` corpus or DB. |
| D3 | Language / toolchain | **Python 3.13 + uv** (lockfile). | Reproducible grader installs. | pip+venv; 3.12. Risk: verify onnxruntime/sqlite-vec wheels on 3.13/Windows at scaffold time. |
| D4 | Agent framework | **PydanticAI.** | Per-request budget (`UsageLimits(per_request_input_tokens_limit, count_tokens_before_request=True)`), `ProcessHistory`/`before_model_request` hooks for compaction that keep tool call/return pairs intact, `prompt_cache_outlook()`, deferred tools/`load_capability` for lazy capability instructions. | Hand-rolled loop (more code, we'd re-implement history integrity); LangGraph (heavy, opaque prompts). |
| D5 | LLM providers | **Claude + Meta + local** behind a thin model factory + our budget/logging hooks. Claude via `anthropic`; Meta and local via PydanticAI's OpenAI-compatible provider. | Swap providers by config. | LiteLLM; OpenAI-compat only. |
| D5a | Models | **Claude Sonnet 5.5** (`claude-sonnet-5-5`, default) · **Meta Muse Spark 1.3 Contributor** (via Meta's API) · **Bonsai 2** hosted locally for offline/cheap testing, through an OpenAI-compatible local server. All chosen by `LLM_PROVIDER` + `LLM_MODEL`. | One code path for every model. A local model lets us iterate without paying per call. | Hard-coded model names. Model IDs for Muse Spark and Bonsai 2 to confirm when keys/servers are set up (NOTES R3). |
| D6 | Budget accounting | Enforced number = `input_tokens + cache_read + cache_creation` (provider-reported). Pre-send count via provider endpoint where available; else local estimate with safety margin. | Anthropic's `input_tokens` excludes cached tokens; we report the defensible number. | Counting `input_tokens` alone. |
| D7 | Retrieval | **Hybrid: SQLite FTS5 + sqlite-vec with local `fastembed` embeddings.** | Robust to paraphrased evaluator variations; no extra API key. | FTS5 only; API embeddings. **Status: Revisit after prototype** (measure whether embeddings earn their weight). |
| D8 | Persistence | **SQLModel** for tables; raw SQL confined to `memory/search.py` for FTS5/vec virtual tables. | Typed models alongside PydanticAI/pydantic. | stdlib sqlite3 raw; SQLAlchemy Core. |
| D9 | Main chat surfaces | **CLI + HTTP API + styled web page.** Overrides the brief's "no styling" (allowed, not required). | Better demo; graders can use CLI or HTTP. | CLI only; unstyled page. |
| D10 | Web UI | **assistant-ui (React) + Vite + TypeScript**, talking to our FastAPI. FastAPI serves the built `web/dist`. | Polished open-source chat components incl. thread list for parallel sessions. | htmx+Pico, Chainlit, Gradio. Cost: Node toolchain. |
| D11 | Slack | **Bolt for Python, Socket Mode.** | No public URL/tunnel needed locally. | Events API + ngrok. |
| D12 | Quality tooling | pytest, ruff, pydantic-settings (`.env`). | Standard, light. | — |
| D13 | Budget guard | Own `BudgetedModel` (a PydanticAI `WrapperModel`) instead of `UsageLimits(count_tokens_before_request=True)`. Pre-flight uses the provider count endpoint for Claude, a conservative local estimate (JSON chars / 3) for Meta and local, with fallback to the estimate if the endpoint fails. Logs every request to `.state/logs/llm_calls.jsonl`. | Works for every provider (Meta/local may lack a count endpoint), and one wrapper catches every call, including future summarizer and extractor agents. PydanticAI already folds cache tokens into `input_tokens`. | Built-in flag only (hard failure on providers without counting). |
| D14 | Recent history | Replay recent turns verbatim from stored PydanticAI runs (whole turns, so tool call/return pairs stay together), up to `HISTORY_TOKEN_BUDGET` (2500). The window start snaps to turn k*`HISTORY_WINDOW_STEP`+1 (8), so it only moves every 8 turns and the prefix stays cacheable. Claude runs with `anthropic_cache=True`. Ingest = same pipeline with the reply generation skipped. | Recent context without loading 500 turns; cache hits between window moves. | Sliding by one turn (cache miss every turn); rebuilding history from plain text only (loses tool exchanges). |
| D15 | Fact memory | An extractor agent (structured output) turns user messages into facts with scope `user`/`thread`/`ephemeral` and a topic key. Ephemeral items are dropped. Same key + scope supersedes the old fact, which is kept with `superseded_at`/`superseded_by`. The chat agent gets a profile block: current facts, each followed by its earlier versions. Runs after the reply on every live turn; every 10 turns during ingest. | Scenario 1 (cross-thread), 4 (change with history), 5 (draft-only stays local), and evaluator variations without special-casing. | Regex/rule extraction (brittle); letting the chat model call a `remember` tool (it forgets to call it; mixes concerns). |
| D16 | Pre-flight counting (rev. D13) | `TOKEN_COUNT_MODE=auto` uses the provider count endpoint for Claude **and Meta**; the local estimate (x`ESTIMATE_SAFETY_FACTOR`=1.5) only for local servers or when the endpoint fails. | Measured: estimate undercounted Meta by up to 31%; Meta's endpoint overcounts (safe). | Estimate for Meta (unsafe); tighter factor. |
| D17 | Long-thread recall | Every message is indexed in FTS5 and sqlite-vec (fastembed `bge-small-en-v1.5`, local). Each chat turn searches turns older than the replayed window (RRF fusion; vector hits need cosine distance <= 0.35) and attaches up to `RETRIEVAL_TOKEN_BUDGET` of snippets to the current message; a `search_history` tool allows follow-up lookups. Stored runs keep only the user's own words. | Detail recall from hundreds of turns ago (scenario 2) at a fixed cost. | Summaries only (lose details); stuffing more history. |
| D18 | Rolling summaries | Fixed 25-turn chunks, each summarized once when >= 16 turns old; the latest 3 before the window go into the instructions. | Gist of older conversation; fixed boundaries keep the block stable for caching. | Re-summarizing a single running summary (drift, loses details, cache-hostile). |
| D19 | Context assembly | Instructions = system + preferences (with history) + summaries. History = aligned recent window. Current message carries relevant facts (ranked, `FACTS_TOKEN_BUDGET`) + snippets. Estimated total is shrunk to `CONTEXT_FILL_RATIO` (0.8) of the budget by dropping snippets → summaries → half history → facts; if pre-flight still refuses, rebuild at 60% then 35%. | Every source bounded; graceful degradation instead of failed turns; real provider counts decide. | One global token cap with truncation at the end (cuts the current message). |
| D20 | Chat prompt caching | Chat uses explicit Anthropic breakpoints (`anthropic_cache_instructions` + a `CachePoint` before the current message) instead of automatic caching. Stored runs drop instructions; replayed tool returns are cut to a deterministic stub. | Instructions + history are reused turn to turn; the volatile current message (with facts/snippets) is never written to cache. Verified live: ~60-75% of chat input read from cache. | Automatic caching (writes the never-reused tail each call; never hit because the augmented message doesn't recur). |
| D21 | Big documents | `fetch_doc` returns full text only for small docs (<= 1,500 tokens); otherwise a note distilled once by map-reduce (section-aware ~7.5k-char chunks → per-chunk notes with verbatim facts → grouped reduce), cached by content hash. `search_doc` returns the best ~1.2k-char passages (FTS5 + vectors) within 1,500 tokens. Docs opened in a thread are listed in later turns' instructions. Doc ids resolve case/punctuation-insensitively, only among files in DOCS_DIR. | A 35k-token doc never enters a prompt; later questions ("that plan") cost one small tool result. | Truncating the doc; embedding-only RAG without a note (misses "summarize"); re-reading per question. |
| D22 | Tool-loop budget | A `ProcessHistory` hook re-fits every request of a turn by dropping the oldest replayed whole turns; core assembly and the hook share one target (`context_target_tokens`, divided by the estimate safety factor when pre-flight can't use a provider count). | Tool results grow later requests of the same turn; context assembly alone can't see them. | Bigger static reserve for tool output (wastes context on most turns). |
| D23 | Memory access (revises D15, D17-D19) | Target: bounded agent-called session and long-term memory read/write/search tools, rather than harness-injected memory blocks. Persist session records without exposing them to other sessions. Detailed lifetime and scope policy remains open. Serialize mutations initially. **Implementation pending**; existing extraction and injection remain until refactored. | User direction, 2026-10-20: the central challenge is managing persistent/local knowledge over 100k+ aggregate tokens with <=8k per request. | Treating all recalled preferences/facts as mandatory prompt content; locking in the current scope taxonomy. |
| D24 | Initial capability loading (revises D4 lazy-loading direction) | Load current tool schemas and instructions upfront; measure actual cost before introducing tool search or dynamic discovery. **Implementation policy**, not a requirement to build discovery now. | Current tool set is small; spend effort on memory and compaction first. | Premature dynamic capability loader. |
| D25 | Context shrinking priority (extends D22) | Prioritise bounded continuation within long tool runs, recoverable evidence and persisted working state. Retain the budget guard; improve estimation separately. Optional search subagents must have bounded inputs/outputs and use the same per-call budget and usage logging. **Implementation pending** beyond existing whole-turn trimming. | Dropping old replayed turns alone cannot shrink an arbitrarily long current run. | Restarting the whole agent run as the only shrink strategy, potentially repeating mutations. |
| D26 | Capability registry (implements D24) | A capability = subpackage of `chatbot.capabilities` exposing `CAPABILITY` (name, one-line description, tools, `instructions.md`), auto-discovered and loaded upfront in name order (stable, cacheable). `chatbot capabilities` reports per-request token cost (now ~900 for 3). Context assembly uses the measured tool + instruction cost. | Adding a capability = adding a folder; cost is visible before deciding on discovery. | Hand-maintained list; lazy loading now. |
| D27 | LinkedIn rules in code | Writer agent returns `body` + `hashtags` separately; an output validator gives one retry with the exact overrun; `validator.assemble` then guarantees the rules (links stripped, inline hashtags unwrapped, <= 3 tags on the last line, trimmed to 1,300 at a sentence). The tool sets the turn's reply to the post verbatim. | Rules can't be broken by either model; the chat model can't re-word the post afterwards. | Asking the model to follow the rules; validating only. |
| D28 | send_message | Records to an `OutboundMessage` table (thread, recipient, text); nothing is delivered. | Inspectable by tests/scenarios; included in forget's sweep (M7). | Log file only. |
| D29 | Memory retrieval architecture (revises D7, D18, D21, D25 search direction) | Persist original messages/passages, source-linked searchable episode notes, versioned long-term records and task checkpoints. Search both raw evidence and summaries with FTS5/BM25; evaluate existing vectors as an additional candidate source and reranking only if measured gains warrant it. **Implementation pending.** | User accepted 2026-10-21: combine precise evidence recall with compact topic navigation without loading a growing title catalog. Persistence is separate from retrieval. | Summaries replacing source evidence; mandatory vector/reranking dependency before measuring recall. |
| D30 | Memory search agent (revises D25 optional-subagent direction) | Main agent calls `ask_memory(question, store)`; a bounded read-only subagent owns query reformulation, search, adjacent/source reads and verification. Trusted dependencies enforce ownership. Return status, concise answer, source references/excerpts and caveats. All calls use the shared budget/log guard; mutations use separate tools. **Implementation pending; contracts/sequence in PLAN.md.** | Keeps exploratory search out of the main context while preserving inspectable evidence and honest incomplete/conflicting outcomes. | Full-catalog scans; unsupported answer-only responses; search agent silently writing/promoting facts. |
| D31 | Memory storage layer (implements PLAN sequence 1; contracts in docs/MEMORY_CONTRACTS.md) | `MemoryRecord` + `RecordSource` with typed refs (`msg:`/`rec:`/`psg:`), ownership from `MemoryCaller` only, invisible = not found, explicit version chains (no forks, no implicit supersede by key), >= 1 original source per write, one process lock + one transaction per mutation incl. the FTS row, tool-call idempotency keys, startup `reindex_missing()` repair, incremental `legacy_fact_id` migration. Not wired to the agent yet. | Gives later steps (memory tools, ask_memory subagent, forget) a store whose guarantees are tested in isolation. | Migration-table flag (reruns would miss facts written after the first run). |
| D32 | Source + note search (PLAN sequence 2) | `EpisodeNote` + `NoteSource` (exact covered message ids; contiguous, non-overlapping, session-private) with `note_fts`. `search_memory` fuses separately ranked BM25 lists over records, raw session messages and notes (+ optional message vectors), owner/store-filtered in SQL, deduplicated per turn, capped at 2,400 excerpt chars, each hit tagged with the lists that found it. Notes are written by maintenance only. | Notes bridge paraphrases and point at exact evidence; raw messages keep their own list, so omitted or wrong note content can't hide a detail (mutation-checked). | Searching notes first and expanding only their messages (summary gates evidence); single merged FTS table (loses per-representation ranking). |
